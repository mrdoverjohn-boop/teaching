# CHALLENGES

These are not normal exercises.

These are meant to be:

- competitive
- stupid
- chaotic
- actually useful
- fun enough that nobody realizes they are practicing programming

You can do most of these with Python.

For team-vs-teacher challenges, the students can use Python while Bramity uses Rust or C.

---

# DIFFICULTY SCALE

## 🟢 Beginner

They know:
- print
- variables
- input
- basic math
- if statements

## 🟡 Early Game Developer

They also know:
- while loops
- for loops
- random
- lists

## 🟠 Intermediate Beginner

They also know:
- functions
- reading other people's code
- organizing a program into sections

## 🔴 Advanced Challenge

They can:
- build small programs without step-by-step instructions
- debug things
- understand unfamiliar code
- plan a tiny game before writing it

---

# CHALLENGE LIST

## 🟡 01 — 30 Minute Game Challenge

Students:
- Python
- may work together

Bramity:
- Rust or C
- works alone

Everyone gets the same theme and 30 minutes.

Folder:
`01_30_minute_game`

---

## 🟠 02 — 100 Line Game

Make the best game possible in 100 lines or less.

This teaches:
- removing repeated code
- functions
- organization
- keeping scope under control

Folder:
`02_100_line_game`

---

## 🔴 03 — Swap Codebases

Everyone starts a game.

Halfway through:

SWAP.

You now have to finish somebody else's program without them explaining it.

This teaches:
- reading unfamiliar code
- understanding someone else's structure
- writing code that other humans can understand

Folder:
`03_swap_codebases`

---

## 🔴 04 — Bug Sabotage

Make a small working program.

Give it to somebody else.

They secretly add bugs.

You get it back and race to fix it.

This teaches:
- debugging
- reading errors
- tracing logic
- staying calm when your code explodes

Folder:
`04_bug_sabotage`

---

## 🟠 05 — Feature Auction

Everyone gets the same starter game and fake money.

Features are auctioned off.

Examples:

- inventory
- random enemies
- healing
- score system
- secret ending
- shop
- boss fight

If you buy a feature, YOU HAVE TO IMPLEMENT IT.

This teaches:
- planning
- scope
- deciding what features are actually worth your time

Folder:
`05_feature_auction`

---

## 🟠 06 — One Hour Game Rescue

Everybody receives a terrible unfinished game.

The code works... kinda.

You get one hour to turn it into the best game possible.

You are allowed to:
- fix it
- add mechanics
- remove bad mechanics
- rewrite sections
- improve the UI/output

This teaches:
- working with existing code
- refactoring
- debugging
- making decisions under time pressure

Folder:
`06_game_rescue`

---

## 🟠 07 — Secret Mechanic

Everyone gets the SAME theme.

But each person secretly gets one required mechanic.

Examples:

- stealing
- trading
- a timer
- fake physics
- inventory
- an NPC
- random events
- multiple endings

Nobody knows anyone else's mechanic until the end.

This teaches:
- adapting an idea around a constraint
- designing around requirements

Folder:
`07_secret_mechanic`

---

## 🔴 08 — Blind API Challenge

Everyone is given a tiny helper file made by someone else.

They are NOT allowed to edit it.

They have to use the provided functions to make a game.

Example helpers might contain things like:

```python
damage_enemy()
heal_player()
random_enemy()
save_score()
```

You have to figure out how to use the provided code instead of rewriting everything yourself.

This teaches:
- using APIs
- reading function signatures
- working with code you did not create

Folder:
`08_blind_api`

---

## 🔴 09 — Final Boss: Students vs Bramity

Students:
- work together
- Python
- full access to the teaching repo

Bramity:
- alone
- Rust
- same amount of time

Everyone gets the same theme.

Recommended time:
60 minutes.

This is the final challenge.

Folder:
`09_students_vs_bramity`

---

# RECOMMENDED ORDER

Do not throw the hardest ones at them immediately.

A good order is:

1. 30 Minute Game
2. 100 Line Game
3. Secret Mechanic
4. Feature Auction
5. Game Rescue
6. Swap Codebases
7. Bug Sabotage
8. Blind API
9. Students vs Bramity

By the time they reach the last few challenges, they should be doing something VERY different from beginner tutorial programming.

They should be:

- planning
- reading code
- debugging
- designing systems
- writing functions
- adapting ideas
- finishing projects

That is the point.

# IMPORTANT RULE

The technically most complicated project does NOT automatically win.

A tiny game that is:
- complete
- funny
- polished
- fun

can absolutely beat a giant broken project.

SHIP THE FUCKING GAME.
